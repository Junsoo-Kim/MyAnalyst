![마이애널리스트 로고 사진](https://github.com/user-attachments/assets/5f5159fb-cc13-4390-9721-ca2768beff28)

MyAnalyst는 기존 기업 분석 보고서가 가진 주관성, 정보의 비실시간성, 높은 접근 장벽의 문제점을 해결하기 위해 탄생한 RAG 기반 기업 분석 보고서 생성 서비스입니다.

사용자는 원하는 기업의 최신 공시 및 뉴스 데이터를 기반으로, 편향성이 배제된 객관적인 분석 보고서를 언제든지 직접 생성할 수 있습니다.  또한, 어려운 금융 용어를 설명해주는 용어 사전과 궁금증을 즉시 해결해주는 AI 비서 기능 등을 통해 누구나 쉽게 보고서를 이해하고 의사 결정에 활용할 수 있도록 돕습니다.

이를 통해 MyAnalyst는 금융 정보의 비대칭성을 해소하고, 모든 투자자가 신뢰할 수 있는 정보에 평등하게 접근하는 새로운 기준을 제시합니다.

## 프로젝트 배경

### 현행 기업 분석 보고서의 문제점

![PPT 문제점 제시](https://github.com/user-attachments/assets/ce2f2183-70a5-43ea-8554-b244bea27ec9)

기업 분석은 특정 기업의 재무 상태, 비즈니스 모델, 경쟁력 등을 체계적으로 평가하여 해당 기업의 현재 및 미래 가치를 판단하는 과정입니다. 이를 기반으로 작성된 기업 분석 보고서는 증권사나 투자 리서치 기관의 전문가들이 투자자들에게 제공하는 중요한 자료입니다.

개인 투자자의 입장에서 기업 분석 보고서는 투자 전략을 수립하고 의사 결정을 내리는 데 중요한 역할을 합니다. 일반 투자자가 기업의 성장 가능성, 재무 안정성, 시장 트렌드를 직접 분석하는 것은 어렵기 때문에, 금융 전문가들이 작성한 보고서를 통해 주가 전망, 리스크 요인, 목표 주가 등 전문적인 정보를 얻습니다. 이를 통해 투자자는 보다 신뢰할 수 있는 데이터를 바탕으로 합리적인 결정을 내릴 수 있습니다.

그러나 현재의 기업 분석 보고서는 몇 가지 한계점이 존재합니다.

첫째로, 현재의 기업 분석 보고서는 분석자의 소속 기관, 투자 성향, 선호도 등에 따라 주관적인 견해가 포함될 가능성이 있습니다. 이는 투자자들이 객관적인 데이터를 바탕으로 판단하기 어렵게 만들고, 특정 분석가의 의견을 맹신하게 하는 부작용을 초래할 수 있습니다. 이로 인한 책임은 개인 투자자가 져야 하기 때문에, 개인 투자자에게는 더욱 객관적이고 중립적인 자료가 필요합니다.

둘째로, 정보의 최신성이 부족합니다. 대부분의 기업 분석 보고서는 분기(약 3개월) 단위로 발간되기 때문에, 시시각각 변화하는 투자 환경에 대한 실시간 반영이 어렵습니다. 특히 급변하는 금융 시장에서는 단기간 내에 중요한 정보가 바뀔 수 있어, 투자자가 시의적절한 결정을 내리기 어렵습니다.

셋째로, 높은 진입장벽이 있습니다. 기업 분석은 방대한 데이터를 수집하고 이를 해석하는 과정에서 많은 시간과 인력이 소요됩니다. 특히 금융 전문가의 경험과 인사이트가 중요한 요소로 작용하기 때문에, 일반 투자자들이 직접 기업 분석을 수행하기에는 높은 진입 장벽이 존재합니다. 이로 인해 금융 기관이나 투자 전문가의 기업 분석 보고서에만 의존할 수 밖에 없다는 한계가 있습니다.

이러한 한계를 극복하기 위해 이 프로젝트에서는 RAG(Retrieval-Augmented Generation) 기술을 활용하여, 보다 발전된 기업 분석 보고서를 생성하고자 합니다.

### RAG 기술을 적용하는 이유

![RAG 설명](https://github.com/user-attachments/assets/48d4d063-d8d2-45b1-bf40-f5b50d2b6220)

RAG는 대규모 데이터를 빠르고 정확하게 검색한 후, 이를 바탕으로 LLM(Large Language Model)이 고도화된 분석을 수행하는 기술입니다. 이를 통해 기존의 기업 분석 방식에서 발생하는 문제점을 보완할 수 있습니다.

첫째로 기업 분석 보고서의 객관성을 강화할 수 있습니다. 기존의 분석 보고서는 작성자의 주관적 해석이 포함될 수 있지만, RAG를 활용하면 정량적인 데이터 분석을 기반으로 보다 객관적인 기업 평가를 수행할 수 있습니다.

둘째로, 기업 보고서에 들어가는 정보의 최신성을 보장할 수 있습니다.사용자가 원하는 시점에 즉시 기업 분석 보고서를 생성할 수 있어, 최신 데이터를 반영한 분석이 가능해집니다. 이는 기존 보고서의 주기적 발간 방식과 비교했을 때 정보의 정확성을 높이는 데 큰 장점이 됩니다.

셋째로 자원 소모가 절감되고 접근성이 향상됩니다. 웹 크롤링 및 LLM을 활용하여 방대한 데이터를 자동으로 수집하고 해석할 수 있어, 기존의 분석 과정에서 요구되던 높은 인력과 시간이 절감됩니다. 또한, 금융 전문가가 아닌 일반 투자자들도 쉽게 기업 분석 보고서를 생성하고 활용할 수 있습니다.

본 프로젝트는 이러한 RAG 기술의 강점을 활용하여 보다 효율적이고 신뢰할 수 있는 기업 분석 보고서를 제공하는 것을 목표로 합니다.

## 기술적 도전과제

### 1. 하이브리드 검색(Dense + BM25) 및 RRF 도입

Challenge:
1번 챌린지에서 구축한 RAG 시스템은 Milvus의 코사인/L2 거리 기반 Dense 벡터 검색만 사용했습니다. 그러나 금융 도메인 텍스트는 수치, 고유명사, 재무 식별자가 자연어 문장과 섞여 있는 경우가 많아, 의미 기반 검색만으로는 정확한 키워드 일치가 중요한 문서를 놓치는 한계가 있었습니다.

Solution:

- Sparse 인덱스 자체 구축: 당시 사용 중인 Milvus 2.4 standalone은 자체 BM25/Sparse 인덱스를 지원하지 않아, `rank_bm25` 라이브러리로 별도의 스파스 인덱스를 구축했습니다.
- 의존성 최소화한 토크나이징: BM25용 형태소 분석기로 KoNLPy 등을 새로 도입하는 대신, 이미 임베딩에 쓰고 있던 KLUE-BERT의 WordPiece 토크나이저를 재사용해 컨테이너 이미지와 배포 복잡도를 늘리지 않았습니다.
- RRF(Reciprocal Rank Fusion) 병합: Dense(거리, 작을수록 좋음)와 Sparse(BM25 점수, 클수록 좋음)는 점수 스케일이 완전히 달라 직접 정규화해 섞기 어렵습니다. 대신 각 검색기 결과 내에서의 순위만 이용하는 RRF(`score = Σ 1/(k+rank+1)`)로 병합해, 두 검색기에서 동시에 상위권에 오른 문서가 최종적으로 상위에 오도록 설계했습니다.
- 안전한 롤백 경로: `HYBRID_SEARCH_ENABLED` 환경변수로 언제든 기존 Dense-only 검색으로 즉시 되돌릴 수 있게 했고, Sparse 인덱스 구축이 실패하거나 코퍼스가 비어 있어도 Dense 결과로 자동 폴백하도록 만들었습니다.

Achievement:
서버 기동 시 BM25 인덱스를 미리 구축하도록 했고, 실제 Milvus 데이터로 인덱스가 정상 구축되는지, RRF 병합 점수가 설계한 공식대로 계산·정렬되는지, 데이터가 없을 때 Dense-only로 안전하게 폴백하는지를 확인할 수 있었습니다.

### 2. LangGraph 기반 Corrective RAG로 환각 억제

Challenge:
기존 파이프라인은 "키워드 생성 → 검색 → 생성"이 단 한 번만 실행되는 완전 선형 구조였습니다. 검색된 문서가 부실하거나 LLM이 컨텍스트를 벗어난 내용을 생성해도, 파이프라인 스스로 이를 감지하고 고칠 방법이 없었습니다.

Solution:

- 상태 그래프 설계: LangGraph로 `generate_keywords → retrieve → grade_documents → generate_section → grade_hallucination`을 잇고, 근거가 부족하다고 판정되면 `rewrite_query`로 검색 키워드를 다시 만들어 재검색하는 조건부 루프를 추가했습니다.
- 비용을 고려한 채점 설계: 검색된 문서마다 개별적으로 LLM을 호출하면 호출 수가 top-k만큼 늘어나므로, 문서 관련성 채점은 후보 전체를 한 번의 배치 호출로 처리하도록 설계했습니다.
- Fail-open 채점: 관련성 채점과 환각 채점 모두, 채점 자체가 실패(API 오류 등)하면 통과시키는 방향으로 설계해 채점 로직의 장애가 보고서 생성 전체를 막지 않도록 했습니다.

Achievement:
LLM 호출부만 스텁으로 대체해 그래프 전체를 실제로 실행하는 방식으로 제어 흐름을 검증했습니다 - "1차 생성 → 근거 부족 판정 → 쿼리 재작성 → 재검색 → 재생성 → 근거 통과 판정 → 종료"로 이어지는 재시도 루프가 설계한 그대로 동작시킬 수 있었습니다.

### 3. AWS 인프라 분리 설계 및 코드화(Terraform)

Challenge:
AWS Academy 교육을 계기로 직접 인프라를 배포·운영해보고자 했습니다. 초기에는 인스턴스 1대에 백엔드, AI 연산, DB를 모두 올리는 방식으로 접근했는데, 임베딩 연산과 DB 검색이 동시에 몰리는 상황에서 자원 고갈로 인한 단일 장애점(SPOF)이 발생했습니다. 이 경험을 계기로 인프라를 근본적으로 재설계하고, 콘솔에서 클릭으로 만드는 대신 재현 가능한 코드로 관리하기로 했습니다.

Solution:

- 3계층 디커플링: 백엔드(Spring Boot), AI 연산(FastAPI), 데이터 계층(RDS/ElastiCache/Milvus)을 VPC 내에서 완전히 분리했습니다. 보안그룹은 "바로 앞 계층에서만" 인바운드를 허용하는 최소 권한 체인으로 설계했습니다 (인터넷 → ALB → BE → RAG → Milvus/RDS/Redis).
- 컨테이너 오케스트레이션과 수평 확장: ECS Fargate로 BE/RAG를 각각 서비스화하고 CPU 사용률 기반 오토스케일링을 붙여, 인스턴스 분리만으로는 해결되지 않던 "계층 내부의 단일 인스턴스 SPOF"까지 줄였습니다.
- 비용 최적화: RAG(임베딩 연산, 중단에 상대적으로 관대함)는 온디맨드 1개 + Fargate Spot 위주로, 진입점인 BE는 100% 온디맨드로 구성해 안정성과 비용을 나눠 가져갔습니다.
- 관측성: ALB 5xx/헬스체크, RDS, ElastiCache, ECS 서비스별 CloudWatch 알람을 SNS로 연결해, 장애를 사후 복구가 아니라 사전에 감지할 수 있게 했습니다.
- CI/CD와 보안: GitHub Actions가 장기 보관되는 AWS 액세스키 없이 OIDC로 임시 자격증명만 받아 배포하도록 구성했고, 그 IAM 역할의 권한도 ECR 푸시/해당 ECS 서비스 업데이트로만 좁혔습니다.
- 점진적으로 켤 수 있는 설계: 도메인이 아직 없어 HTTPS는 ACM 인증서 ARN의 유무로 켜지고 꺼지는 조건부 리소스로 만들어뒀습니다 - 나중에 인증서만 발급받으면 코드 변경 없이 활성화됩니다.

Achievement:
클라우드에 실제로 올리기 전, 로컬 Docker Compose로 동일한 3계층 통신 경로(BE → RAG → Milvus/RDS/Redis)를 실제로 띄워 헬스체크와 서비스 간 통신을 확인했고, Redis 캐싱도 실제 요청을 통해 캐시 히트가 발생하는 것까지 검증했습니다.
